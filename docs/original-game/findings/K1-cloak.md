# K1 — Personal Cloaking Field (`AGENT_GENERAL_TYPE_CLOAKING_FIELD`, `0x0a`)

## Verdict

> **NOT BOUND — closed negative.** All 19 functions that read `agent_general_data`'s `type`
> field in this session's live `OpenApocOG_TACP` Ghidra project were examined. Three of them
> *recognize* type `0x0a` (a UI status-icon picker, an AI equip-priority `×0xc` scoring case, and
> an AI combat order-preference check — the last one new this session). **None implements a
> concealment/detection-suppression effect.** No accumulator, threshold-compare, "is-concealed"
> flag, detection-radius modifier, or break-on-fire logic exists anywhere in the traced code. The
> third recognizer's downstream order handler was traced to a plain per-unit decay counter with no
> dispatch semantics — see "New consumer #3" below for the full trace, including where an initial
> reading in this session was wrong and how it was corrected.
>
> Cloaking Field is structurally identical to Vortex Analyzer / Structure Probe / Alien Detector
> (G1): recognized by catalog entry, inventoriable, and consulted by UI/AI bookkeeping, but with
> **zero implemented runtime gameplay effect** in TACP.EXE. Do not invent a tick-based concealment
> mechanic for OpenApoc's `BattleUnit::updateCloak`/visibility code on the strength of this binary;
> there is nothing here to port. If OpenApoc keeps a passive cloak effect, it is prior art with no
> original-game basis — say so in the parity guide rather than presenting it as recovered.
>
> This also directly answers the parity guide's framing of the blocker ("cloak tick thresholds
> unbound"): `FUN_00066474` (candidate #17 below) **is** the per-unit tick dispatcher — reached on
> the 36-vanilla-tick cadence from the same main-loop caller (`FUN_00011620`) that drives Mind
> Shield's and Disruptor Shield's cadences, and the exact function where Mind Shield's
> `+30/cap 200` regen lives. Under the repository's observational 36-TPS compatibility canon that
> interval is one game-second; the binary site itself binds the interval, not absolute cadence. It
> has **no case for type `0x0a` at either hand-slot block**. There is no tick site in the original
> that reads or compares a cloak-engage threshold, because the one function that would host it
> doesn't have one.

### Order-type `0x11` trace — fully resolved

`FUN_00021008` (page-file `0x11007`) is a **generic fixed-pool allocator** — `DAT_0011f118`,
0x16-byte stride, 0x91 (145) slots — used by roughly 70 call sites across the entire AI subsystem
(weapon-fire decisions, movement decisions, teleport decisions, etc.), not specific to any item
type. It is not itself a cloak mechanism.

Its consumer/dispatcher is `FUN_0003d9e4` (page-file `0x2d9e3`, size 9598 bytes) — a giant
`switch` on the order-type byte, with 18 cases (`0x01`–`0x13`). Case `0x11` (listing captured in
`export/query_k1_order_dispatch.log`) branches on whether `*(short*)(order+4)==0` (a second field
inside the order record) and, along the way, calls `FUN_00023960()`, `FUN_00041e10()`, then
`FUN_000a2c98()` — the exact "is this item a Motion Scanner (type `0x01`)" predicate examined as
candidate #6 above — before falling through to path/travel-related calls (`FUN_0005b770`,
`FUN_000c5275`, `FUN_0003702c`) or, on the non-zero branch, writing `(&DAT_0010a182)[uVar24] = 6`
and `(&DAT_0010a180)[unit*0x24e] = <hand item ref>`.

An advisor review flagged three specific gaps in the first pass of this trace, each chased down
and closed:

**1. What does `FUN_000a2c98()` actually get called with?** Listing-verified this session
(`export/query_k1_order11_detail.log`) at the two real call sites (`0x3e804`, `0x3e988` —
page-file `0x2e803`/`0x2e987`; the `0x3e809`/`0x3e98d` addresses in the decompile are the
*return*-address markers, 5 bytes past the `CALL`). Both sites compute `EAX` as: read the
hand-slot's equipment-instance index from `unit+0x30`/`unit+0x32`, multiply by the instance
stride `0x30`, then read the catalog-item-id byte at `[instance+2]` and sign-extend it into `EAX`
before the call. So `FUN_000a2c98(EAX=<that hand's own held item's catalog id>)` — the reading
"gated on Motion Scanner ownership" is correct and now directly confirmed from the call-site setup,
not merely inferred from the callee's identity.

**2. What does `unit+0x2B2` (`DAT_0010a182`) actually mean, and who reads it?** This is the load-
bearing question, because an initial read of this session mischaracterised it as a "pending
hand-action type" field that order `0x11` sets to `6` — implying a possible undiscovered
dispatcher keyed on that value. **That reading was wrong.** Full xref sweep on
`0x10a17e`/`0x10a180`/`0x10a182`/`0x10a183` (32 raw xrefs on `0x10a182` alone,
`export/query_k1_pendingaction_xrefs.log`) plus decompiles of the three smallest, most legible
readers/writers (`export/query_k1_pendingaction_readers.log`) show:

- **`FUN_000583b8`** (page-file `0x483b7`), called every frame from the same main-loop caller
  (`FUN_00011620`) that drives Mind Shield's and Disruptor Shield's tick cadence, does, for every
  unit:
  ```c
  if (DAT_000e6c24 < unit[0x2b2])  unit[0x2b2] -= (byte)DAT_000e6c24;
  else                             unit[0x2b2] = 0;
  ```
  — i.e. `unit+0x2B2` is a **plain decaying byte counter**, ticked down by the same
  game-speed-scaled catch-up amount used elsewhere in this codebase (F1/G1's documented cadence
  variable), clamped to zero. There is a second, parallel counter at `unit+0x2B6` decayed by the
  same function. This is the *only* per-frame consumer of this byte.
- **`FUN_000582b8`** and **`FUN_00057c28`** (the other two heavy readers/writers) both treat
  `unit+0x2B2`/`unit+0x2B4` as part of an "active/selected hand-item" bookkeeping pair — writing
  the `0xff`/`0xffff` invalid-sentinel into it when an item runs out of ammo or gets swapped out —
  consistent with, not contradicting, the Mind Shield tick dispatcher's (`FUN_00066474`, candidate
  #17) documented use of the *adjacent* word `unit+0x2B4` as a hand-slot-2 equipment-instance
  index. Neither function contains a `switch`/compare against a small constant set keyed on this
  field's value.
- Of the 32 raw xrefs to `0x10a182` (and 24/31/1 on the sibling fields), the four decompiled above
  — the per-frame updater plus the three next-heaviest readers/writers — account for the field's
  only non-order-dispatcher consumers; none of the four contains a comparison that branches on
  this field's numeric value as a discriminant. The remaining raw-xref sites were not individually
  decompiled. Order `0x11` writing `6` into it reads as seeding a **cooldown/decay counter**
  ("don't re-evaluate this hand's action for ~6 tick-units"), not tagging a dispatch case — the
  per-frame updater's unconditional decay-to-zero arithmetic is incompatible with the field ever
  being read as a stable "case" tag afterward.

**Conclusion: there is no "type-6 pending-action reader" to find, because the field is a decay
counter, not a dispatch key.** The loop closes here: order type `0x11`'s own body never touches
`DAT_002b2e7a`/`0x2b2854`/`0x2b2855` (the general-equipment lookup) at all, and neither does
anything that reads what it writes. It cannot discriminate on cloak vs. any other trigger reason
(weapon fallback, Teleporter fallback — both of which also write this same generic record via
`FUN_0003c1c4`), and nothing downstream of it discriminates either.

**3. Trigger-condition wording — left unsettled, deliberately.** `FUN_0008f338`'s guard
(`*(int*)(&DAT_0010a17e + unit*0x24e) >> 0x10 == -1`) reads the same field
(`unit+0x2AE`/`DAT_0010a17e`) that `FUN_00066474`'s Mind Shield check uses as a hand-slot
equipment-instance index, which supports reading the guard as "no item in this hand" — but
`FUN_000582b8`'s swap logic (candidate reader above) manipulates the same field alongside a
worn/active flag (`+5` byte on the equipment-instance record) in a way that reads more like
"currently active/selected item in this hand" than either "equipped item" or "target." Three
readings remain live — no assigned item, no active/selected item, no target — and this document
does not pick one. It does not need to: none of the three changes the bottom line, since under any
of them the guard is testing a generic per-hand state bit that has nothing to do with the general-
equipment type table, and the order it queues has no cloak-specific effect regardless of why it
fired.

## Re-verification of `FUN_0008a524` case `10` (the previously-known consumer)

The prior doc's citation of "case 10/0xa, sharing the gated ×0xc multiplier with Mind Shield
(case 5) and Disruptor Shield (case 8)" could not be re-derived from a fresh decompile in this
session — the function is 7355 bytes and the decompiler output truncates (30000-char cap) before
reaching this code in both this session's query and the pre-existing dedicated log
(`export/query_cloak_candidate_8a524.log`, itself also truncated). Re-derived instead from the
**raw instruction listing and the actual jump table**, bypassing the decompiler:

- Dispatch site, bound-file `0x8be47`/`0x7be46` (page-file):
  ```
  MOV AL, byte ptr [EDX + 0xa]   ; type field
  DEC AL
  CMP AL, 0xb                    ; range-check type in [1, 0xc]
  JA  default
  JMP dword ptr [EAX*4 + 0x8a4f4]  ; 12-entry jump table, index = type-1
  ```
- Jump table dump (`scripts/QueryJumpTable.java`, `export/query_k1_8a524_jumptable.log`):

  | type | target VA | case |
  |---|---|---|
  | 1 (Motion Scanner) | `0x8be61` | own body |
  | 2,3,4,7,11 (Structure Probe, Vortex Analyzer, MultiTracker, Alien Detector, DimForceField) | `0x8c0aa` | shared default/no-op path |
  | 5 (Mind Shield) | `0x8be8f` → falls to `0x8beba` | gate flag `DAT_00305808`, then `IMUL EBP,EBP,0xc` |
  | 6 (Mind Bender) | `0x8bec2` | own body (×0x18, calls `FUN_00093664`) |
  | 8 (Disruptor Shield) | `0x8bf18` → falls to `0x8bf43` | gate flag `DAT_00305814`, then `IMUL EBP,EBP,0xc` |
  | 9 (Teleporter) | `0x8bf4b` | calls `FUN_000952b8` (the Teleporter-% function, candidate #15 above) |
  | **10 (Cloak)** | `0x8c063` → falls to `0x8c086` | gate flag `DAT_0030581c`, then `IMUL EBP,EBP,0xc` |
  | 12 (Medi-kit) | `0x8c08b` | own body |

**Correction to the prior doc's wording**: types 5, 8, and 10 do **not** share code — they are
**three distinct case bodies falling through to three distinct gate-flag checks**
(`DAT_00305808`, `DAT_00305814`, `DAT_0030581c` respectively — each presumably "does the squad
already have one of these equipped/worn somewhere" or similar), which **converge on the identical
`IMUL EBP,EBP,0xc` arithmetic** before jumping to a shared finalizer at `0x8c0d8`. The ×0xc
scoring-multiplier claim is correct and now independently re-verified from raw bytes (not just
re-cited); "sharing the multiplier" should read "sharing the *formula*," not the code path. This
remains a **priority score consumed only at equip-selection time** (deciding what to auto-equip an
agent with) — not a battle-tick concealment effect. This part of the verdict is unchanged.

## What was ruled out

No accumulator, threshold-compare, "is-concealed" flag write, detection-radius modifier, or
break-on-fire logic exists in any of the 19 examined functions, nor in the order-type-`0x11` trace
that a third recognizer (`FUN_0008f338`) leads into. Specifically ruled out, not merely unfound:

- A per-unit "ticks cloaked so far" accumulator comparable to OpenApoc's
  `CLOAK_TICKS_REQUIRED_UNIT`/`battleunit.cpp:2114` accumulator — searched via the complete xref
  set on the general-equipment type table and via the order-queue trace; nothing increments or
  compares such a value gated on type `0x0a`.
- A "break cloak on fire" hook — the weapon-fire code path (`FUN_0008f338`'s weapon-category
  branch, and the two hand-slot blocks of `FUN_0003c1c4`) never reads the general-equipment table
  for the *other* hand or applies any cloak-specific side effect when firing.
- A detection/spotting-radius modifier reading equipment type — not found in this table's 19
  readers. To check for a reader that reaches the type field through a non-literal addressing
  pattern the row0+10 xref scan would miss, enumerated every function referencing the two
  upstream lookup bytes the idiom is built on (`DAT_002b2854` category byte, 96 raw xrefs;
  `DAT_002b2855` subtype-index byte; union 64 unique functions,
  `export/query_k1_category_xrefs.log`) and subtracted the 19 already examined — **44 residual
  functions**. Rather than read all 44, ran a second, independent check: a full literal-xref sweep
  of the *entire* `agent_general_data` table region (all ~20 rows × 12 bytes,
  `export/query_k1_table_range_xrefs.log`) — this catches any function touching *any* field of the
  table by any literal addressing path, not just the type field. Result: **31 unique functions
  touch the table at all; subtracting the 19 leaves 12**, and every one of those 12 was confirmed
  (from the exact target addresses in the same log) to land on a *different* field — the table-base
  pointer load shared by any field access, offset `+1` (a capacity-like field), offset `+6` (the AI
  scoring "value" field used in `FUN_0008a524`), or offset `+8` — never offset `+0xa` (type). So of
  the 44 category/subtype-byte readers, the ones that go on to touch the general-data table at all
  are already accounted for, and none of them reaches the type field by any literal path this
  method can see. This is an enumerated result, not a plausibility argument about compiler
  idioms — but it is still an *xref-based* method, so see the residual caveat below.

## What remains unexamined (explicitly out of scope for this row)

- Whatever code implements enemy-vision/spotting checks in TACP was not traced end-to-end for a
  general "is this unit concealed" predicate that might be set by some mechanism *other than*
  reading `agent_general_data`'s type field directly (e.g. a per-unit flag set once at
  equip-time by code this session's xref method could not reach). This is the same category of
  residual uncertainty the project's own B3 write-up flags as unavoidable with address-based
  search — recorded here rather than papered over.
